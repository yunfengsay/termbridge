# Voice 消融：真实云端结果与流式修复复测

日期：2026-09-05。协议与复现入口见 [评测设计](voice-ablation.md)。
本轮是探索性实验，不是模型准确率榜单。前 30 次是修复前调查；后续 8 次与源码修复见末节，尚未部署/真机验收。

## 样本与条件

共 30 次真实 `qwen3.5-omni-flash-realtime` 调用：2 次基线验证、16 次术语×语境、
8 次降噪对照、4 次降噪分块对照。未请求模型版本快照，重复不能外推至未来服务端版本。
样本均为固定合成语音，16kHz PCM16LE mono，无用户私密录音。

- 技术句，7.623 秒：请打开 TermBridge，启动 Codex Agent，检查 Skill 和 LLM 的状态，然后读取今天的日历。
- 中文反例，3.871 秒：请把图片缩放到一半，不要修改颜色。

默认术语：TermBridge、Herdr、Codex、Claude Code、Token、LLM、Skill、Agent、PTY、Cloudflare。
场景语境为项目/Worker 名和讨论主题，未给完整期望转录。每轮从全新云端会话开始。
这只是新会话短句评测，不代表连续多轮自然对话已经通过。

复用生产 `BailianRealtimeConversation` 与 `buildVoiceFrontendInstructions`，保持 semantic VAD、
音频格式、温度和工具 schema。工具后端固定 mock，不执行用户任务；仅核验转交契约。
独立语音输入的 Qwen ASR API、Android 麦克风/系统 DSP/Silero 门控不在本轮云端因子对照中。

## 1. 术语与语境未改善本轮技术句字幕

| 条件 | 技术句原始转录 CER，第 1 / 2 次 | 技术句 Fork 输入 CER | 中文反例异常 |
|---|---|---|---|
| baseline：10 术语，无场景语境 | 6.25% / 6.25% | 0 / 0 | 0 / 2 |
| no-vocabulary：无术语，无场景语境 | 6.25% / 6.25% | 0 / 0 | 2 / 2：有最终转录，无工具调用 |
| context：10 术语＋场景语境 | 6.25% / 10.42% | 0 / 0 | 1 / 2：有工具调用，无 completed 转录 |
| context-only：无术语＋场景语境 | 6.25% / 10.42% | 0 / 0 | 1 / 2：有最终转录，无工具调用 |

异常均按 55 秒 deadline 记录，不通过重试洗掉失败。16 次共 4 次未满足本轮完整观察条件。
其中 3 次是语音前端未调用工具，而非 ASR 无字；另 1 次已经正确转交，但缺少最终转录事件，
不能描述为执行失败。进一步判断模型回答了什么，需要专项回放，不能仅凭 deadline 归因。

拿到最终转录的中文反例均为正确的“缩放”，未观察到被强改为 Skill。
所有技术句最终转录均出现 SKU，工具参数却恢复成 Skill；这发生在应用 reconciliation
之外：本轮应用提交文字仍是 SKU，原始 tool-call 参数已经是 Skill。
因此语音理解/生成工具参数与字幕不是同一份文本，不能只凭字幕断言模型没听懂。
相反，也不能保证这种隐式改写总正确，否定词、真实 SKU 场景需加入测试。

结论：本轮不能证明“扩大通用词表/加场景段落”能改善 ASR。
也不能因此删除上下文或术语：样本太少，且移除术语后出现转交不稳定。
不能将其解释为术语导致成功的统计因果；需更多句子与重复，单独拆开提示词与 reconciliation。

## 2. 当前分块降噪对技术词产生可复现退步

Android 模拟器中运行项目同一 `sherpa-onnx-1.13.6-arm64.aar` 和 `gtcrn_simple.onnx`，
单线程 CPU。探针镜像 `OnDeviceVoiceModels.denoise` 的 run/量化/fallback 过程。
不包含门控，不模拟厂商麦克风 NS/AEC，也不是三星真机性能测试。

| 技术句输入 | 第 1 次 CER | 第 2 次 CER | 主要错误 |
|---|---:|---:|---|
| 未做 GTCRN 的原音 | 6.25% | 6.25% | Skill → SKU |
| 同模型 256ms 分块输出 | 22.92% | 22.92% | TermBridge → TurnBridge；Codex → Products；Skill → SKU |
| 同模型整句一次输出 | 10.42% | 10.42% | TermBridge → TurnBridge；Skill → SKU |

分块对照阶段又重复两次 256ms 输出，仍为 22.92%。整句处理只改变 run 的输入块长，
没有换模型/词表；当时支持“分块调用方式会影响音频保真”的假设。后续源码核验确认
每次 offline Run 都重新初始化频谱与模型状态，详见末节及架构文档。

两种降噪条件下中文“缩放”反例的原始转录均正确。技术句传给 Fork 的文字最终仍正确，
不代表受损音频没有产品风险，只说明此句后续语义处理补救成功。

模拟器处理诊断（不含模型初始化）：技术句分 30 块共 181.3ms，整句 166.1ms；
两者 RMS 比率分别约 0.9474 和 0.9969。不能把这些数当手机端实时延迟或降噪质量分数。
两个条件末尾均使用 109 个 fallback 样本；真实 Call 的尾块刷新策略不在本探针范围。

**优先研究有状态流式增强/连续窗口与正确拼接，不直接把生产 Call 改为整句等待。**
真实风噪样本缺失，所以不能据此关闭降噪或认定车内效果已改善。

## 3. 延迟、资源、失败证据边界

大部分首字约 1.0–1.1 秒，工具首次调用通常在输入语音末尾后约 1.7–2.0 秒。
这些包含实时喂音节奏、semantic VAD 和网络，不是模型纯推理时延。
部分后期实验与构建/另一评测进程短暂重叠；本轮不做条件间的延迟优劣排名。
原音/分块降噪阶段的音频条件顺序固定，后续分块/整句阶段已反转顺序；正式实验需随机配对。

每条本机私有 JSONL 保存输入 hash、prompt hash、model、测试文本、原始最终转录、
应用提交文字、工具调用、精选事件与 usage。未记录 AK、请求 headers、完整 session 或音频字节。
usage 是供应商返回的使用量，不等于已结算费用。本轮没有测耗电或内存峰值。

## 产品决策

1. 保留联网 Omni 与默认提示词，不用这两句话的结果调整全产品默认。
2. 优先处理输入保真：当前分块增强有实测退步，比“再加关键词”更值得先查。
3. 字幕/理解/工具转交分层可追踪。不要用关键词硬替换掩盖字幕问题。
4. 对已接受的用户 turn，派发必须有稳定 ID、去重、超时与可恢复状态；不应只靠模型
   每次都主动调用工具。是否由 Host 确定性触发 Fork，需要和 Omni 音频理解纠正能力一起消融。
5. 有界、相关且带时效的上下文仍是复杂连续对话的候选必需项；本轮没有验证其代词消歧收益。
6. 暂不新增独立 ASR/重写模型，不扩大成全量 Memory/History 灌入；先用真实用户语音复核。

下一批必测：真实 SKU vs Skill、Codex 名称、否定/撤销、长句过 10 秒、轻声词头、车内风噪、
车载蓝牙、打断后续说、指代当前图片/Agent、多轮工具超时恢复。

## 流式修复与后续 8 次云端复测

新增 `OnlineDenoiseReplay.java`，在同一 Android 模拟器、同一 GTCRN/AAR 中跑真正的在线接口，
输入 512 / 4096 / 200000 samples 三种块长。技术句输出均为 243930 bytes，与输入等长，
SHA-256 均为 `c1fb2ef1258218c8ef35d2d9f36711a561dd6811d12cb957c0bdf10697740665`。
无 raw fallback；表明状态连续且输出不依赖喂入块长。512 模式处理 7.623 秒音频耗时约 257.7ms，
仅为模拟器离线计算时间，不是三星耗时或音频首包延迟。

随后相同云端 baseline 对原音/在线降噪各重复两次、两个样本，共 8 次。第二轮反转音频顺序。

| 条件 | 技术句 raw CER（两次） | 技术句 Fork CER | 中文反例 |
|---|---|---|---|
| 原音 | 10.42% / 6.25% | 0 / 0 | 转录均正确；一次无工具 |
| 新 Online GTCRN | 10.42% / 10.42% | 0 / 0 | 转录正确，两次均转交工具 |

对照旧 offline 分块的 22.92%，新接口消除了本样本 Codex → Products 退步，但没有消除
TermBridge/Skill 的全部字幕错误，也没有证据证明降噪比干净原音更准确。
全 8 次为 7 次完整链路、1 次无工具；不能声称 8/8 成功。累计 38 次调用中仍有 5 条缺少
预期的完整事件序列（分别为缺工具/缺 final），不是已修复所有执行问题。

本次失败样本原始字幕、应用 final 都正确，assistant 却回答：
“好的，我会把图片缩放到原来的一半大小，同时保持颜色不变。请问您现在需要我执行这个操作吗？或者您有其他需求？”
约 7.9 秒收到 response.done，却没有 fork_execution，55 秒按实验 deadline 结束。
这明确区分了听写问题与未遵守派发契约，而不是将二者混成“ASR 蠢”。
